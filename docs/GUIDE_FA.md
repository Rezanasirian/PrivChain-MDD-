## ۱) پروژه در یک نگاه

### مسئله‌ای که حل می‌کنیم
می‌خواهیم از روی **مصاحبهٔ بالینی** یک فرد تشخیص دهیم آیا نشانه‌های **افسردگی** دارد یا نه.
هر مصاحبه سه نوع داده (سه «وجه» یا modality) دارد:

- **صدا (audio):** صوت گفتار فرد.
- **تصویر (video):** حالت چهره فرد.
- **متن (text):** متن پیاده‌شدهٔ حرف‌هایش.

برچسب (label) هر فرد از پرسش‌نامهٔ استانداردی به نام **PHQ-8** می‌آید: نمره‌ای بین ۰ تا ۲۴.
طبق قرارداد رایج، نمرهٔ **۱۰ یا بیشتر = افسرده (۱)** و کمتر = غیرافسرده (۰).

### سه ایدهٔ نوآورانه که این پروژه را خاص می‌کند
1. **حریم خصوصی تفاضلی به‌ازای هر وجه (H1):** دادهٔ پزشکی فوق‌العاده حساس است. ما با
   اضافه‌کردن «نویز» از فاش‌شدن هویت افراد جلوگیری می‌کنیم — اما **به‌اندازهٔ ریسک هر وجه**.
   صدا بیشتر از همه فرد را لو می‌دهد (از صدا می‌شود فرد را شناخت)، پس بیشترین نویز را می‌گیرد.
2. **یادگیری فدرال با دسترسی نامتقارن (H2):** داده در یک‌جا جمع نمی‌شود؛ هر بیمارستان داده
   خودش را نگه می‌دارد و فقط مدل را آموزش می‌دهد. بعضی بیمارستان‌ها فقط صدا دارند، بعضی فقط
   متن، بعضی هر سه. باید با این **ناهمگنی** کنار بیاییم.
3. **لایهٔ حسابرسی روی بلاک‌چین (H3):** اینکه «چه‌قدر بودجهٔ حریم خصوصی خرج شد» روی یک دفترکل
   تغییرناپذیر (بلاک‌چین Hyperledger Fabric) ثبت می‌شود تا قابل حسابرسی باشد.

> **وضعیت فعلی:** فازهای ۰ تا ۶ پیاده شده‌اند. فاز ۷ (خطوط پایهٔ مقایسه‌ای و ارزیابی نهایی)
> و فاز ۸ (نوشتن فصل‌های ۳ تا ۵ پایان‌نامه) هنوز مانده‌اند.

## ۲) مفاهیم پایه‌ای که باید بفهمی

این بخش را اگر بخوانی، بقیهٔ سند راحت می‌شود. هر مفهوم با یک مثال روزمره.

### ۲.۱ یادگیری ماشین و «مدل» یعنی چه؟
یک **مدل (model)** مثل یک تابع ریاضی بزرگ است که ورودی می‌گیرد و خروجی می‌دهد. مثلاً ورودی =
داده‌های یک مصاحبه، خروجی = «افسرده / غیرافسرده». این تابع تعداد زیادی **عدد قابل تنظیم** دارد
که به آن‌ها **پارامتر (parameter)** یا **وزن (weight)** می‌گوییم.

**آموزش (training)** یعنی این وزن‌ها را آن‌قدر تغییر دهیم تا مدل روی نمونه‌هایی که جوابشان را
می‌دانیم، کمترین اشتباه را بکند.

> تشبیه: مثل پیچ‌های یک رادیوی قدیمی. اول صدا پر پارازیت است؛ پیچ‌ها (وزن‌ها) را کم‌کم
> می‌چرخانی تا صدا (پیش‌بینی) واضح شود.

### ۲.۲ تنسور (Tensor)
**تنسور** فقط یعنی «آرایه‌ای از اعداد». یک عدد تنها، یک بردار (لیست عدد)، یک ماتریس (جدول
عدد)، یا چیزهای بزرگ‌تر — همه تنسورند. در PyTorch همه‌چیز تنسور است.

- نمرهٔ یک فرد: تنسور صفر-بُعدی (یک عدد).
- ویژگی‌های صدای یک فرد در طول زمان: تنسور دو-بُعدی به شکل `(تعداد فریم زمانی، تعداد ویژگی)`.
- یک «دسته/بَچ (batch)» از چند فرد: تنسور سه-بُعدی `(تعداد افراد، زمان، ویژگی)`.

«شکل (shape)» تنسور یعنی همین اندازه‌هایش. بخش بزرگی از کد ما مطمئن می‌شود شکل‌ها درست‌اند.

### ۲.۳ PyTorch چیست؟
یک **کتابخانهٔ پایتون** برای ساختن و آموزش مدل‌ها. دو کار اصلی برایمان می‌کند:
1. محاسبات روی تنسورها (ضرب ماتریس و …).
2. **گرادیان** را خودکار حساب می‌کند (پایین‌تر توضیح می‌دهیم).

### ۲.۴ گرادیان و «گرادیان نزولی» (Gradient Descent)
فرض کن خطای مدل یک «تپه» است و ما در دامنه‌اش ایستاده‌ایم. می‌خواهیم به پایین‌ترین نقطه
(کمترین خطا) برسیم. **گرادیان** یعنی «جهت شیب رو به بالا». پس برای پایین‌رفتن، **خلاف
گرادیان** قدم برمی‌داریم. هر قدم، وزن‌ها را کمی اصلاح می‌کند. اندازهٔ هر قدم را **نرخ یادگیری
(learning rate)** می‌گویند.

این چرخه (پیش‌بینی → محاسبهٔ خطا → گرادیان → اصلاح وزن) را آن‌قدر تکرار می‌کنیم تا مدل خوب شود.
یک بار عبور کامل روی همهٔ داده‌ها را یک **epoch** می‌گویند.

### ۲.۵ «وجه/مودالیتی» (Modality) و «چندوجهی» (Multimodal)
هر **نوع داده** یک وجه است: صدا، تصویر، متن. مدل ما **چندوجهی** است یعنی هم‌زمان از هر سه
استفاده می‌کند، چون ترکیب آن‌ها دقیق‌تر از تک‌تکشان است (مثل اینکه برای فهمیدن حال کسی، هم به
لحن صدا، هم چهره، هم حرف‌هایش توجه کنی).

### ۲.۶ اِنکودر (Encoder) و فیوژن (Fusion)
- **اِنکودر:** بخشی از مدل که یک وجه را می‌گیرد و آن را به یک **بردار خلاصه (embedding)**
  تبدیل می‌کند. مثلاً «انکودر صدا» کل صدای یک نفر را به یک بردار مثلاً ۶۴‌تایی فشرده می‌کند که
  جانِ مطلب صدا را دارد.
- **فیوژن:** بردارهای سه وجه را **به هم می‌چسباند/ترکیب می‌کند** تا یک بردار واحد بسازد که
  بعد به آن «سرِ تصمیم‌گیری» داده می‌شود.

### ۲.۷ یادگیری فدرال (Federated Learning)
به‌جای اینکه دادهٔ همهٔ بیمارستان‌ها را در یک سرور جمع کنیم (که برای دادهٔ پزشکی خطرناک و
گاهی غیرقانونی است)، **مدل را نزد داده می‌فرستیم**:

1. سرور یک نسخه از مدل را به هر بیمارستان (**کلاینت/client**) می‌دهد.
2. هر کلاینت مدل را با دادهٔ **محلی خودش** کمی آموزش می‌دهد.
3. کلاینت‌ها فقط **وزن‌های به‌روزشده** را برمی‌گردانند (نه داده را).
4. سرور این وزن‌ها را **میانگین می‌گیرد** و مدل بهتری می‌سازد.
5. این چرخه (**round/دور**) بارها تکرار می‌شود.

ساده‌ترین روش میانگین‌گیری **FedAvg** نام دارد: میانگین وزن‌ها با وزن‌دهی به‌اندازهٔ تعداد
دادهٔ هر کلاینت.

### ۲.۸ حریم خصوصی تفاضلی (Differential Privacy یا DP)
سؤال کلیدی: «اگر دادهٔ یک نفر را از مجموعه حذف کنیم، آیا خروجی مدل محسوس فرق می‌کند؟» اگر
فرق نکند، یعنی مدل **هویت آن فرد را حفظ نمی‌کند** و حریم خصوصی‌اش امن است.

DP این را با **اضافه‌کردن نویز تصادفی** به گرادیان‌ها تضمین می‌کند. دو پارامتر دارد:
- **اپسیلون ε:** «بودجهٔ حریم خصوصی». ε **کوچک‌تر = حریم خصوصی قوی‌تر** (نویز بیشتر، اما دقت
  کمتر). ε بزرگ‌تر = حریم ضعیف‌تر، دقت بهتر. پس یک **بده‌بستان (trade-off)** است.
- **دلتا δ:** احتمال کوچک شکست تضمین (مثلاً ۱۰⁻⁵).

دو کار فنی برای DP در آموزش (که به آن **DP-SGD** می‌گویند):
1. **بریدن گرادیان هر نمونه (per-sample gradient clipping):** سهم هر فرد در به‌روزرسانی را به
   یک سقف `C` محدود می‌کنیم تا هیچ‌کس تأثیر بیش‌ازحد نگذارد.
2. **افزودن نویز گاوسی (Gaussian noise):** به مجموع گرادیان‌ها نویز اضافه می‌کنیم. مقدار نویز
   با عددی به نام **ضریب نویز σ (sigma)** کنترل می‌شود. σ بزرگ‌تر = نویز بیشتر = ε کوچک‌تر.

**حسابدار حریم خصوصی (Privacy Accountant):** ابزاری که می‌گوید «با این σ و این تعداد قدم،
چه‌قدر ε خرج شده؟» ما از روش **RDP** (نوعی حساب‌داری ریاضی دقیق) استفاده می‌کنیم.

### ۲.۹ نوآوری ما: DP «به‌ازای هر وجه»
معمولاً به کل مدل یک ε واحد می‌دهند. ولی صدا، تصویر و متن **ریسک لورفتن هویت یکسانی ندارند**:
از صدا راحت‌تر می‌شود فرد را شناخت تا از متن. پس ما به هر وجه یک ε جدا می‌دهیم:
صدا (ریسک بالا) → ε کوچک → نویز زیاد؛ متن (ریسک پایین) → ε بزرگ → نویز کم. این همان **H1** است.

### ۲.۱۰ بلاک‌چین
یک **دفترکل تغییرناپذیر**: وقتی چیزی روی آن نوشته شد، دیگر کسی نمی‌تواند پنهانی عوضش کند.
ما مقدار ε خرج‌شدهٔ هر کلاینت را روی آن ثبت می‌کنیم تا **قابل حسابرسی** باشد (پیاده‌سازی در فاز ۵).

## ۳) ساختار پوشه‌ها چه می‌گوید

```
privchain-mdd/
├── configs/          ← همهٔ «تنظیمات و اعداد» اینجاست (هیچ عددی داخل کد ثابت نمی‌شود)
│   ├── baseline.yaml   تنظیمات داده و مدل و آموزش
│   ├── federated.yaml  تنظیمات یادگیری فدرال (تعداد کلاینت‌ها و …)
│   └── privacy.yaml    تنظیمات حریم خصوصی (ε و ریسک هر وجه)
├── src/privchain/    ← خودِ کد
│   ├── data/           ساختن دادهٔ ساختگی + خواندن دادهٔ واقعی DAIC-WOZ
│   ├── encoders/       انکودرهای صدا/تصویر/متن
│   ├── fusion/         ترکیب وجه‌ها + مدل کامل
│   ├── privacy/        حریم خصوصی تفاضلی (حسابدار، تخصیص بودجه، DP-SGD)
│   ├── federated/      یادگیری فدرال (کلاینت، تجمیع، شبیه‌سازی)
│   ├── training/       حلقهٔ آموزش، تابع خطا، ثبت نتایج
│   ├── eval/           معیارها (F1، ROC-AUC) + مدل‌های حمله (فاز ۶)
│   ├── chain_client/   پل پایتون ↔ بلاک‌چین Fabric (فاز ۵)
│   └── config.py       خواندن و اعتبارسنجی فایل‌های configs
├── chaincode/          ← قرارداد هوشمند Go برای بلاک‌چین (فاز ۵)
├── scripts/          ← فایل‌های اجرایی (آموزش، فدرال، آزمایش حریم خصوصی)
├── tests/            ← تست‌ها (مطمئن می‌شوند کد درست کار می‌کند)
├── docs/             ← مستندات (همین فایل + ADRها)
└── experiments/      ← خروجی هر اجرا (نتایج، نمودارها، چک‌پوینت مدل)
```

**چرا configs جداست؟** چون یک اصل مهم پروژه این است: **هیچ عددی (مثل نرخ یادگیری یا ε) داخل
کد نوشته نمی‌شود.** همه از فایل‌های YAML می‌آیند تا آزمایش‌ها قابل‌تکرار و قابل‌تغییر باشند.

**ADR چیست؟** در `docs/architecture/` فایل‌هایی به نام ADR (Architecture Decision Record)
هست. هرکدام **یک تصمیم مهم طراحی** و دلیلش را ثبت می‌کند. مثل دفترچهٔ «چرا این‌طوری ساختیم».

## ۴) فاز ۰ — آماده‌سازی محیط و دادهٔ ساختگی

### هدف
قبل از هر کدی، یک پایهٔ **قابل‌تکرار** بسازیم و — چون دادهٔ واقعی DAIC-WOZ هم حساس است و هم
حجمش ۳۰۰ گیگابایت و فقط با مجوز در دسترس است — یک **دادهٔ ساختگی (mock)** بسازیم که شکلش
دقیقاً مثل دادهٔ واقعی باشد تا بتوانیم کل خط لوله را بدون دادهٔ واقعی تست کنیم.

### دادهٔ ساختگی یعنی چه؟
عددهای **تصادفی** با همان شکل دادهٔ واقعی:
- صدا: ماتریس `(تعداد فریم، ۴۰)`
- تصویر: ماتریس `(تعداد فریم، ۴۹)`
- متن: ماتریس `(تعداد توکن، ۶۴)`
- نمرهٔ PHQ-8: عددی بین ۰ تا ۲۴، و برچسب = (نمره ≥ ۱۰).

> نکتهٔ مهم: چون این داده **تصادفی محض** است، هیچ «الگوی واقعی» در آن نیست. پس **دقت مدل روی
> این داده بی‌معنی است** — فقط برای تست کردنِ اینکه «لوله‌کشی درست کار می‌کند» به‌کار می‌رود.
> اعداد واقعی وقتی می‌آیند که روی DAIC-WOZ واقعی آموزش بدهی.

### تکرارپذیری (Reproducibility) و «بذر/seed»
کامپیوتر برای تولید عدد تصادفی از یک **بذر (seed)** شروع می‌کند. اگر بذر یکسان باشد، همان
دنبالهٔ «تصادفی» دوباره تولید می‌شود. ما همه‌جا seed را از config می‌خوانیم تا **هر بار همان
نتیجه** بیاید (برای فصل ۴ پایان‌نامه که نتایج باید قابل‌تکرار باشند، حیاتی است).

### در کد کجاست؟
- `src/privchain/data/mock_daic_woz.py` — کلاس `MockDaicWozDataset` که این داده را می‌سازد،
  به‌علاوهٔ تابع `collate_fn` (پایین توضیح می‌دهیم) و `build_dataloader`.
- `src/privchain/seeding.py` — تابع `seed_everything` که PyTorch و NumPy و random را با یک
  بذر تنظیم می‌کند.
- `src/privchain/config.py` — با کتابخانهٔ **pydantic** فایل‌های YAML را می‌خواند و
  **اعتبارسنجی** می‌کند (اگر عددی غلط باشد، همان اول خطا می‌دهد).

### مفهوم «دیتاست» و «دیتالودر» و «کولِیت»
- **Dataset (دیتاست):** یک شیء که می‌توانی بگویی «نمونهٔ شمارهٔ ۵ را بده» و آن نمونه را
  می‌سازد/می‌خواند.
- **DataLoader (دیتالودر):** نمونه‌ها را در **دسته‌های (batch)** کوچک بسته‌بندی می‌کند تا
  آموزش سریع‌تر و پایدارتر شود.
- **مشکل طول متغیر:** هر فرد طول صدای متفاوتی دارد (یکی ۸۰ فریم، یکی ۲۰۰). برای اینکه بتوانیم
  چندتا را در یک ماتریس بگذاریم، کوتاه‌ترها را با **صفر پُر (padding)** می‌کنیم تا هم‌اندازه
  شوند. تابع `collate_fn` این کار را می‌کند و در کنارش **طول واقعی** هر نمونه را هم نگه می‌دارد
  (که بعداً نویز صفرها در محاسبات تأثیر نگذارد).

### تعریف «انجام‌شده» برای فاز ۰
یک تست `pytest` روی خط لولهٔ دادهٔ ساختگی اجرا شود و **تنسورهایی با شکل درست** تولید کند.
(تست‌ها در `tests/unit/test_mock_daic_woz.py` و `tests/integration/test_pipeline_smoke.py`.)

## ۵) فاز ۱ — مدل پایهٔ چندوجهی

### هدف
یک مدل بسازیم که **بدون** پیچیدگی فدراسیون و حریم خصوصی، فقط از روی سه وجه، افسردگی را
پیش‌بینی کند. این «سقف دقت» ماست؛ بعداً که فدراسیون و نویز اضافه شود، می‌بینیم چه‌قدر دقت
فدا می‌شود.

### معماری مدل (سه تکه)
```
صدا  → [انکودر صدا]  → بردار ۶۴‌تایی ┐
تصویر → [انکودر تصویر] → بردار ۶۴‌تایی ├─ [فیوژن: چسباندن] → [سرِ تصمیم] → احتمال افسردگی
متن  → [انکودر متن]  → بردار ۶۴‌تایی ┘
```

#### ۵.۱ انکودرها — چطور یک «دنبالهٔ زمانی» را خلاصه می‌کنیم؟
هر وجه یک **دنباله در طول زمان** است (مثلاً صدا = دنباله‌ای از فریم‌ها). انکودر ما سه گام دارد
(`src/privchain/encoders/sequence_encoder.py`):

1. **تصویرسازی خطی (Linear projection):** هر فریم را به یک فضای پنهان (مثلاً ۶۴‌بُعدی)
   می‌برد. «خطی» یعنی یک ضرب ماتریسی ساده.
2. **GRU (یک نوع شبکهٔ بازگشتی):** فریم‌ها را **به‌ترتیب زمانی** می‌خواند و حافظه نگه می‌دارد.
   تشبیه: مثل خواندن یک جمله کلمه‌به‌کلمه که معنی را در ذهنت می‌سازی. («GRU» نوعی واحد حافظه‌دار
   است؛ جزئیات داخلی‌اش مهم نیست، فقط بدان «دنباله را می‌فهمد».)
3. **میانگین‌گیری ماسک‌دار (masked mean-pooling):** خروجی همهٔ فریم‌ها را میانگین می‌گیرد تا یک
   بردار واحد شود. «ماسک‌دار» یعنی **فریم‌های پُرشده با صفر (padding) را نادیده می‌گیرد** —
   اینجاست که آن «طول واقعی» که در collate نگه داشتیم به‌کار می‌آید.

برای هر وجه یک کلاس جدا داریم (`encoders/audio.py`، `video.py`، `text.py`) که همگی از همین
انکودر مشترک ساخته شده‌اند — تا کد تکرار نشود ولی ساختار تمیز بماند.

#### ۵.۲ فیوژن — ترکیب سه بردار
`src/privchain/fusion/multimodal_fusion.py` سه بردار ۶۴‌تایی را **به‌هم می‌چسباند** (می‌شود
۱۹۲‌تایی) و با یک لایهٔ خطی به یک بردار ترکیبی تبدیل می‌کند. نکتهٔ آینده‌نگرانه: یک ورودی به
نام **presence (حضور)** دارد که می‌گوید کدام وجه‌ها واقعاً موجودند — این برای فاز ۲ که بعضی
کلاینت‌ها وجه ندارند، لازم می‌شود.

#### ۵.۳ سرهای تصمیم‌گیری (Heads)
`src/privchain/fusion/baseline_model.py` کل مدل را می‌سازد و دو «سر» دارد:
- **سرِ طبقه‌بندی (classification head):** یک عدد می‌دهد به نام **logit**. با تابع
  **sigmoid** به احتمالی بین ۰ و ۱ تبدیل می‌شود (احتمال افسرده‌بودن).
- **سرِ رگرسیون (regression head، اختیاری):** خودِ نمرهٔ PHQ-8 را هم تخمین می‌زند. این یک
  «کار کمکی» است که معمولاً یادگیری را بهتر می‌کند (به آن **multi-task** می‌گویند).

#### ۵.۴ تابع خطا (Loss)
**خطا/loss** عددی است که می‌گوید مدل چه‌قدر اشتباه کرده؛ هدف آموزش، **کمینه‌کردن** آن است.
`src/privchain/training/objective.py` دو خطا را جمع می‌کند:
- **BCE (Binary Cross-Entropy):** برای سرِ طبقه‌بندی — هرچه احتمالِ پیش‌بینی‌شده به برچسب
  واقعی نزدیک‌تر، خطا کمتر.
- **MSE (Mean Squared Error):** برای سرِ رگرسیون نمرهٔ PHQ-8 — مربع تفاوت پیش‌بینی و واقعیت.

#### ۵.۵ حلقهٔ آموزش (Trainer)
`src/privchain/training/trainer.py` کلاس `CentralizedTrainer` همان چرخهٔ بخش ۲.۴ را اجرا
می‌کند: برای هر epoch → برای هر batch → پیش‌بینی، خطا، گرادیان، اصلاح وزن. بعد از هر epoch
روی دادهٔ **اعتبارسنجی (validation)** که مدل آن را ندیده، معیارها را حساب می‌کند و بهترین مدل
را ذخیره می‌کند.

#### ۵.۶ معیارها (Metrics)
`src/privchain/eval/metrics.py`:
- **Accuracy (دقت):** چند درصد پیش‌بینی‌ها درست بود.
- **F1:** میانگین هماهنگ «precision» و «recall»؛ وقتی کلاس‌ها نامتوازن‌اند (مثلاً افراد افسرده
  کم‌اند) از دقت معیار بهتری است.
- **ROC-AUC:** توانایی مدل در **رتبه‌بندی درست** (احتمال اینکه یک فرد افسردهٔ تصادفی نمرهٔ
  بالاتری از یک غیرافسردهٔ تصادفی بگیرد). ۱.۰ عالی، ۰.۵ مثل سکه‌انداختن.

### دادهٔ واقعی DAIC-WOZ
`src/privchain/data/daic_woz.py` نوشته شده تا دادهٔ واقعی را با **همان شکل** دادهٔ ساختگی
بخواند (صدا از فایل‌های COVAREP، تصویر از OpenFace، متن از فایل‌های ترنسکریپت). برای متن، چون
مدل از پیش‌آموزش‌دیده نداریم و آفلاین هستیم، از یک روش ساده به نام **هَشینگ (hashing)** برای
تبدیل متن به عدد استفاده می‌شود. این بخش هنوز روی دادهٔ واقعی اجرا نشده (چون دانلود نشده) ولی
کدش آماده است (جزئیات در ADR-0002).

### تعریف «انجام‌شده» برای فاز ۱
مدل روی دادهٔ ساختگی آموزش/ارزیابی شود و F1 و ROC-AUC گزارش دهد. ✅ انجام شد.

## ۶) فاز ۲ — یادگیری فدرال با کلاینت‌های ناهمگن

### هدف
همان مدل فاز ۱ را **توزیع‌شده** آموزش بدهیم: داده پیش کلاینت‌ها می‌ماند، فقط وزن‌ها رد و بدل
می‌شود (بخش ۲.۷). و چالش اصلی: کلاینت‌ها **وجه‌های متفاوتی** دارند (ناهمگن).

### الگوهای دسترسی به وجه
در `configs/federated.yaml` چهار نوع کلاینت تعریف شده (مثلاً برای ۱۰ کلاینت):
- **full (۴۰٪):** هر سه وجه را دارد.
- **audio_text (۳۰٪):** فقط صدا و متن.
- **audio_only (۲۰٪):** فقط صدا.
- **text_only (۱۰٪):** فقط متن.

بردار **capability = [audio, video, text]** با ۰ و ۱ نشان می‌دهد هر کلاینت چه دارد. مثلاً
`[1,0,1]` یعنی صدا و متن دارد، تصویر ندارد.

### وقتی یک وجه نیست چه می‌کنیم؟
در این فاز عمداً ساده‌ترین (و ضعیف‌ترین) کار را می‌کنیم: وجهِ نبوده را با **صفر** پر می‌کنیم
(`ModalityMaskedDataset` در `src/privchain/federated/partition.py`). یعنی مثلاً برای کلاینت
بدون تصویر، ورودی تصویر یک ردیف صفر است.

**چرا عمداً ساده؟** چون می‌خواهیم **نشان بدهیم این روش ساده افت دقت دارد**؛ همین مشاهده، انگیزهٔ
فاز ۴ است که روش هوشمند را می‌آورد. (این خودش یک نتیجهٔ فصل ۴ پایان‌نامه است.)

### اجزای کد فدرال (`src/privchain/federated/`)
- **partition.py:** داده را بین کلاینت‌ها تقسیم می‌کند و به هرکدام یک capability می‌دهد.
- **client.py:** کلاس `FederatedClient` — هر کلاینت یک نسخهٔ مدل و دادهٔ خودش را دارد؛ متد
  `fit` وزن سرور را می‌گیرد، چند epoch محلی آموزش می‌دهد، و وزن جدید را برمی‌گرداند.
- **aggregation.py:** تابع `fedavg` — میانگین وزن‌دار وزن‌ها (وزن‌دهی به‌اندازهٔ تعداد دادهٔ هر
  کلاینت).
- **simulation.py:** **سرور شبیه‌سازی‌شده** — همهٔ دورها (rounds) را اجرا می‌کند: پخش وزن →
  آموزش محلی کلاینت‌ها → میانگین‌گیری → ارزیابی مدل سراسری → ثبت معیارها.

### دو «backend»: شبیه‌ساز خودمان و Flower
پایان‌نامه می‌گوید از کتابخانهٔ **Flower** برای فدراسیون استفاده شود. اما Flower در این محیط
**نصب نیست** (آفلاین). برای همین:
- یک **شبیه‌ساز داخلی** نوشتیم (`simulation.py`) که آفلاین کار می‌کند و **تست‌شده** است.
- یک **آداپتور Flower** (`flower_app.py`) نوشتیم که **همان** کدِ کلاینت/تجمیع را زیر Flower
  اجرا می‌کند؛ ولی چون Flower نصب نیست، فعلاً اجرا نشده (با `pip install flwr` فعال می‌شود).
هر دو از یک هستهٔ مشترک استفاده می‌کنند، پس کار دوباره‌ای انجام نشده. (جزئیات: ADR-0003.)

### تعریف «انجام‌شده» برای فاز ۲
آموزش فدرال روی **حداقل ۳ کلاینت ناهمگن** اجرا شود و معیارها ثبت شوند. ✅ انجام شد (۸ کلاینت،
۴ الگو، با شبیه‌ساز داخلی).

## ۷) فاز ۳ — حریم خصوصی تفاضلی به‌ازای هر وجه

این **نوآوری اصلی اول (H1)** است. سه تکه دارد: حسابدار، تخصیص بودجه، و DP-SGD.

### ۷.۱ حسابدار RDP (`src/privchain/privacy/accountant.py`)
این بخش به سؤال «با این مقدار نویز σ و این تعداد قدم، چه‌قدر بودجهٔ ε خرج شده؟» جواب می‌دهد.
- ورودی‌ها: σ (ضریب نویز)، q (نرخ نمونه‌گیری = اندازهٔ بَچ ÷ کل داده)، T (تعداد قدم‌ها)، δ.
- خروجی: ε خرج‌شده.
- پایه‌اش ریاضیات استانداردی به نام **RDP مکانیزم گاوسی نمونه‌گیری‌شده** است (مرجع: Mironov
  2019). همان چیزی که Opacus هم درون خودش حساب می‌کند؛ ما آن را آفلاین و دستی پیاده کردیم.
- دو تابع کلیدی:
  - `get_epsilon(σ, q, T, δ)` → ε خرج‌شده.
  - `get_noise_multiplier(ε هدف, q, T, δ)` → σ لازم برای رسیدن به آن ε (با جست‌وجوی دودویی،
    چون ε با بزرگ‌شدن σ کم می‌شود).

ما این را آفلاین صحت‌سنجی کردیم: وقتی q=1 باشد به فرمول سادهٔ `α/(2σ²)` می‌رسد؛ ε با σ کم و با
تعداد قدم زیاد می‌شود؛ و رفت‌وبرگشت σ↔ε درست درمی‌آید.

### ۷.۲ تخصیص بودجه به‌ازای هر وجه (`src/privchain/privacy/budget_allocator.py`)
این **قلب نوآوری** است. دو حالت دارد (در `configs/privacy.yaml`):
- **explicit (صریح):** خودت برای هر وجه ε را می‌دهی. الان: صدا=۲، تصویر=۴، متن=۸.
- **inverse_risk (معکوس ریسک):** یک بودجهٔ کل ε_total می‌دهی و فرمول، آن را **برعکسِ ریسک**
  بین وجه‌ها تقسیم می‌کند:

  ```
  ε_m = ε_total × (r_m)^(−γ) / Σ_k (r_k)^(−γ)
  ```
  یعنی وجهِ پرریسک‌تر (صدا)، ε کوچک‌تر (نویز بیشتر) می‌گیرد. γ شدت حساسیت به ریسک است
  (γ=0 یعنی همه برابر).

سپس برای هر وجه، با حسابدار، σ_m را حساب می‌کند تا دقیقاً به آن ε برسد. و می‌تواند **ε مصرف‌شدهٔ
تا الان** را گزارش دهد — همان چیزی که باید روی بلاک‌چین ثبت شود و **هرگز پنهانی بازنویسی نشود**.

نتیجهٔ واقعی اجرا:
| وجه | ریسک | ε هدف | σ (نویز) |
|----|-----|------|---------|
| صدا | ۰.۹ | ۲.۰ | ۳.۰۰ (بیشترین نویز) |
| تصویر | ۰.۶ | ۴.۰ | ۱.۷۶ |
| متن | ۰.۳ | ۸.۰ | ۱.۱۱ (کمترین نویز) |

دقیقاً همان منطق: **ریسک بیشتر → نویز بیشتر.**

### ۷.۳ DP-SGD به‌ازای هر وجه (`src/privchain/privacy/dp_sgd.py`)
این همان آموزش با حریم خصوصی است (بخش ۲.۸). تفاوت کلیدی ما: **هر وجه یک مکانیزم DP مستقل** است.
گام‌ها برای هر بَچ:
1. پارامترهای مدل را به **گروه** تقسیم می‌کنیم: گروه صدا، گروه تصویر، گروه متن، و گروه
   «مشترک» (فیوژن و سرها). این تقسیم بر اساس نام پارامترها انجام می‌شود.
2. برای **هر نمونه به‌تنهایی**، گرادیان را حساب و **در هر گروه جدا** به سقف `C` می‌بریم
   (per-sample clipping). (روش «میکروبَچ»: یک‌به‌یک جلو/عقب می‌رویم.)
3. به مجموع گرادیانِ **هر گروه**، نویز گاوسی با σ مخصوص همان وجه اضافه می‌کنیم.
4. گروه مشترک، برای امنیت بیشتر، **بیشترین σ** بین وجه‌ها را می‌گیرد.
5. با گرادیان نوزی‌شده، وزن‌ها را به‌روز می‌کنیم.

این دقیقاً همان کاری است که Opacus انجام می‌دهد؛ چون Opacus آفلاین نصب نیست، ما مکانیزم را
مستقیم پیاده کردیم. فایل `opacus_engine.py` یک «پل» است که اگر Opacus نصب باشد، اعداد حسابدار
ما را با Opacus **مقایسه/صحت‌سنجی** می‌کند.

### ۷.۴ نمودار «دقت در برابر ε» (`scripts/run_dp_sweep.py`)
تعریف «انجام‌شده» فاز ۳: (الف) گزارش بودجهٔ مصرف‌شدهٔ هر وجه، (ب) رسم نمودار دقت برحسب ε.
این اسکریپت چند مقدار ε را امتحان می‌کند، برای هرکدام مدل را با DP-SGD آموزش می‌دهد، و
دقت/F1/ROC-AUC را رسم می‌کند (`accuracy_vs_epsilon.png`). انتظار داریم با ε بزرگ‌تر، دقت بهتر
شود (نویز کمتر). **روی دادهٔ ساختگی نمودار صاف است** چون داده الگو ندارد؛ روی دادهٔ واقعی
شیب‌دار می‌شود. (جزئیات: ADR-0004.)

## ۸) فاز ۴ — تجمیع آگاه‌به‌قابلیت + اعتبار + تقطیر فدرال

این **نوآوری اصلی دوم (H2)** و کامل‌کنندهٔ آن است. در فاز ۲ ساده‌ترین کار را کردیم (پرکردن با
صفر) و گفتیم این عمداً ضعیف است. حالا در فاز ۴ آن را با **سه ایده** درست می‌کنیم.

### ۸.۱ مشکل دقیقاً چه بود؟
یک کلاینت «فقط‌متن» ورودی صدا و تصویرش صفر است. وقتی سرور با FedAvg **همهٔ** وزن‌ها را یک‌کاسه
میانگین می‌گیرد، به‌روزرسانیِ **بی‌سیگنالِ** انکودر صدای این کلاینت، انکودر صدای مدل سراسری را
به‌سمت جوابِ پوچ می‌کشد — و دقیقاً به همان کلاینت‌هایی که وجه کم دارند بیشترین آسیب می‌رسد.
سه ایدهٔ زیر این را برطرف می‌کنند.

### ۸.۲ تجمیع زیرگراف آگاه‌به‌قابلیت (`federated/capability.py` و `aggregation.py`)
ایدهٔ اصلی: **هر انکودرِ وجه فقط بین کلاینت‌هایی میانگین گرفته شود که واقعاً آن وجه را دارند** —
به این مجموعه **زیرگراف (subgraph)** آن وجه می‌گوییم.

- پارامترهای مدل بر اساس نامشان **گروه‌بندی** می‌شوند (همان قرارداد فاز ۳): `encoders.audio.*` →
  گروه صدا، `encoders.video.*` → تصویر، `encoders.text.*` → متن، و فیوژن+سرها → گروه «مشترک».
- برای وجه m، فقط کلاینت‌هایی که در بردار capability آن‌ها m=۱ است در میانگین شرکت می‌کنند.
- گروه «مشترک» بین **همهٔ** کلاینت‌ها میانگین گرفته می‌شود (چون همه فیوژن و سر دارند).
- اگر در یک دور **هیچ** کلاینتی وجه m را نداشته باشد، پارامترهای آن انکودر **دست‌نخورده** می‌ماند
  (همان مقدار سراسری قبلی) — نه اینکه با میانگینِ بی‌سیگنال بازنویسی شود.

تابع `capability_aware_aggregate` این کار را می‌کند. نتیجه: هر انکودر فقط از **سیگنال واقعی**
یاد می‌گیرد و آن آلودگیِ صفرها از بین می‌رود.

### ۸.۳ وزن‌دهی بر اساس اعتبار (`federated/reputation.py`)
در هر دور به هر کلاینت یک **امتیاز اعتبار (reputation)** بین ۰ و ۱ می‌دهیم که دو سیگنال را
ترکیب می‌کند:

- **حجم داده:** کلاینتی با دادهٔ بیشتر، سهم بیشتری در میانگین می‌گیرد (مثل FedAvg).
- **سازگاری به‌روزرسانی (consistency):** میزان **هم‌جهت‌بودن** به‌روزرسانی کلاینت با «اجماع»
  زیرگراف، که با **شباهت کسینوسی (cosine similarity)** سنجیده می‌شود. کلاینتی که خلافِ اجماع
  حرکت کند (مثلاً دادهٔ خراب یا مخرب دارد) امتیاز کم می‌گیرد و کم‌وزن می‌شود — یک **محافظت سبک
  در برابر خطاهای بیزانسی (Byzantine)**.

این امتیاز با یک **میانگین متحرک نمایی (EMA)** بین دورها هموار می‌شود تا یک دورِ پرنویز همه‌چیز
را خراب نکند. وزن نهایی هر کلاینت = `max(اعتبار، کف) × حجم`. آن «کف» (`min_reputation`) تضمین
می‌کند هیچ کلاینتِ شرکت‌کننده **کاملاً** حذف نشود.

> اگر در config مقدار `reputation_weighting: false` بگذاری، این به وزن‌دهی سادهٔ حجمی (مثل
> FedAvg) برمی‌گردد، ولی همچنان قاعدهٔ زیرگراف را رعایت می‌کند.

نکتهٔ مهم برای فاز ۵: عکسِ اعتبار هر کلاینت (به‌ازای هر وجه) در فایل `reputation.jsonl` ثبت
می‌شود — دقیقاً همان چیزی که تابع `UpdateReputation` روی بلاک‌چین در فاز بعد ثبت خواهد کرد.

### ۸.۴ تقطیر فدرال برای کلاینت‌های ناقص‌وجه (`federated/distillation.py`)
یک کلاینت «فقط‌متن» نمی‌تواند **وابستگی‌های بین‌وجهی** را از دادهٔ خودش یاد بگیرد.
**تقطیر دانش (knowledge distillation)** این دانش را منتقل می‌کند:

- **معلم (teacher):** مدل سراسریِ **منجمدشده** در ابتدای هر دور.
- **دانش‌آموز (student):** مدل محلی خودِ کلاینت.
- به تابع خطای محلی یک **جملهٔ اضافه** می‌افزاییم که پیش‌بینی‌های **نرمِ** دانش‌آموز را به
  پیش‌بینی‌های معلم نزدیک می‌کند (روی همان دادهٔ محلی). چون تجمیع آگاه‌به‌قابلیت (۸.۲) انکودرهای
  معلم را **تمیز** نگه داشته، پیش‌بینیِ معلم حاوی همان سیگنال بین‌وجهی است که کلاینت کم دارد.

پارامتر `temperature` پیش‌بینی‌ها را «نرم‌تر» می‌کند و `apply_to` تعیین می‌کند فقط کلاینت‌های
ناقص‌وجه تقطیر شوند یا همه. معلم منجمد است پس هیچ گرادیانی به آن نشت نمی‌کند. این قابلیت از طریق
آرگومان‌های **اختیاری** متد `FederatedClient.fit` وصل شده، پس رفتار فاز ۲ بدون آن‌ها دست‌نخورده
می‌ماند.

### ۸.۵ مقایسه با فاز ۲ (`scripts/run_capability_federated.py`)
تعریف «انجام‌شده» فاز ۴ این است: **بهبود قابل‌اندازه‌گیری F1/ROC-AUC نسبت به FedAvg ساده،
به‌ویژه برای کلاینت‌های ناقص‌وجه.** این اسکریپت **هر دو** روش را روی **یک** تقسیم‌بندی، بذر و
مدل اولیهٔ یکسان اجرا می‌کند و فایل `comparison.json` را می‌نویسد: F1/ROC-AUC **کلی** و
**به‌ازای هر الگوی دسترسی وجه** (full، audio_text، audio_only، text_only). این‌طور می‌شود دید
روش هوشمند دقیقاً برای کلاینت‌های ناقص چه‌قدر بهتر عمل می‌کند.

> **روی دادهٔ ساختگی این اختلاف بی‌معنی است** (چون داده الگو ندارد، مثل فازهای قبل)؛ ساختارِ
> مقایسه آماده است و روی DAIC-WOZ واقعی عددِ واقعی می‌دهد. به همین دلیل تست‌ها به‌جای «اختلاف
> دقت روی نویز»، درستیِ **مکانیزم** را بررسی می‌کنند: جداسازی زیرگراف، ترتیب درست اعتبار،
> کمینه‌شدن خطای تقطیر وقتی دانش‌آموز به معلم می‌رسد، و ثبت درست لاگ‌ها. (جزئیات: ADR-0005.)

### تعریف «انجام‌شده» برای فاز ۴
✅ انجام شد (در سطح مکانیزم): هر سه جزء پیاده و تست شدند (۱۹ تست جدید)، اسکریپت مقایسه اجرا
می‌شود و لاگ‌ها/گزارش `comparison.json` را می‌نویسد. عددِ بهبودِ واقعی با دانلود DAIC-WOZ می‌آید.

## ۹) فاز ۵ — لایهٔ بلاک‌چین و حسابرسی

این **نوآوری سوم (H3)** است: همه‌چیز را **قابل حسابرسی** می‌کنیم. هر بار که کلاینتی مقداری از
بودجهٔ حریم خصوصی (ε) خرج می‌کند، اعتبارش عوض می‌شود، یا سرور تصمیم می‌گیرد کدام کلاینت‌ها با هم
تجمیع شوند — این‌ها روی یک **دفترکل تغییرناپذیر** ثبت می‌شود که کسی نتواند بعداً پنهانی عوضش کند.

### ۹.۱ بلاک‌چین و «قرارداد هوشمند» یعنی چه؟
- **بلاک‌چین (blockchain):** دفترکلی که فقط می‌شود به آن **اضافه** کرد؛ حذف/ویرایش پنهانی ممکن
  نیست. مثل دفتری که صفحه‌هایش شماره‌دار و مهرشده‌اند.
- **Hyperledger Fabric:** یک بلاک‌چین **خصوصی/سازمانی** (نه عمومی مثل بیت‌کوین) که برای شبکه‌ای
  از سازمان‌های مورد اعتماد (مثلاً چند بیمارستان) ساخته شده.
- **قرارداد هوشمند (smart contract / chaincode):** برنامه‌ای که **روی خودِ بلاک‌چین** اجرا
  می‌شود و قواعد نوشتن را تعیین می‌کند. در Fabric به آن **chaincode** می‌گویند و با زبان **Go**
  نوشته می‌شود.

### ۹.۲ چهار تابع قرارداد (`chaincode/privchain-cc/`)
قرارداد ما چهار کار اصلی (+ چند تابع خواندن) دارد:
- `RegisterClient(clientID, capability)` — ثبت یک کلاینت و بردار قابلیتش (یک‌بار؛ تکراری رد
  می‌شود).
- `LogPrivacyBudget(clientID, modality, round, epsilon)` — ثبت ε خرج‌شده. **فقط‌افزودنی
  (append-only):** اگر برای همان (کلاینت، وجه، دور) دوباره بنویسی، رد می‌شود — چون ε مصرف‌شده
  هرگز نباید پنهانی بازنویسی شود (اصل مهم پروژه).
- `UpdateReputation(clientID, modality, score, round)` — به‌روزرسانی اعتبار (این چون طبیعتاً هر
  دور عوض می‌شود، قابل‌به‌روزرسانی است).
- `PublishSubgraph(round, [clientIDs])` — ثبت اینکه کدام کلاینت‌ها در این دور با هم تجمیع شدند.
  **تغییرناپذیر:** یک دور فقط یک‌بار ثبت می‌شود.

هر تابع ورودی‌هایش را **اعتبارسنجی** می‌کند و در صورت خطا پیام صریح می‌دهد (هیچ‌وقت crash
نمی‌کند). هرکدام هم یک **تست** با ابزار `shimtest` (یک بلاک‌چین قلابی برای تست) دارد.

> **کدام داده تغییرناپذیر است و چرا:** بودجهٔ ε و زیرگراف تغییرناپذیرند (حقایق تاریخی که نباید
> عوض شوند)؛ اعتبار قابل‌به‌روزرسانی است. این تصمیم‌ها در ADR-0006 مستند شده‌اند.

### ۹.۳ پل پایتون ↔ بلاک‌چین (`src/privchain/chain_client/`)
کد پایتون ما باید با این قرارداد حرف بزند:
- یک **رابط یکسان** به نام `LedgerClient` تعریف کردیم (چهار تابع بالا + خواندن).
- دو پیاده‌سازی:
  - **`MockLedger`** (دفترکل درون‌حافظه‌ای): شبیه‌سازی که **دقیقاً همان قواعد** قرارداد را رعایت
    می‌کند (فقط‌افزودنی بودن ε، تغییرناپذیری زیرگراف). آفلاین کار می‌کند و تست‌شده است.
  - **`FabricRestLedger`** (مسیر واقعی): با یک شبکهٔ واقعی Fabric از طریق یک **دروازهٔ REST** حرف
    می‌زند.
- تابع `build_ledger` از روی config تصمیم می‌گیرد کدام را بسازد. پس بقیهٔ کد نمی‌داند (و لازم هم
  ندارد بداند) پشتِ صحنه دفترکل واقعی است یا قلابی.

### ۹.۴ اتصال به حلقهٔ فدرال (`scripts/run_federated_with_ledger.py`)
در هر دور، اگر یک دفترکل به شبیه‌ساز فدرال داده شود، این‌ها روی آن **نوشته** می‌شوند: زیرگراف آن
دور، ε مصرف‌شدهٔ هر وجه (از حسابدار فاز ۳)، و اعتبار هر وجه. اسکریپت بعد از اجرا، دفترکل را
**می‌خواند** و یک `audit_report.json` می‌سازد — پس هم نوشتن و هم خواندن واقعی داریم (تعریف
«انجام‌شده» فاز ۵).

### ۹.۵ مقاومت بیزانسی (`federated/robust.py`)
یک محافظت اضافه: قبل از تجمیع، کلاینت‌هایی که به‌روزرسانیشان **پرت (outlier)** است (خیلی
بزرگ‌تر از بقیه، احتمالاً خراب یا مخرب) با یک قاعدهٔ آماری مقاوم (median/MAD) کنار گذاشته می‌شوند
— الهام‌گرفته از Sho و همکاران (۲۰۲۴). با فلگ `byzantine_filter` روشن می‌شود و هیچ‌وقت بیش از
نیمی از کلاینت‌ها را حذف نمی‌کند.

### تعریف «انجام‌شده» برای فاز ۵
✅ انجام شد در سطح مکانیزم: قرارداد Go با تست‌های MockStub، پل پایتون، اتصال به حلقهٔ فدرال
(خواندن/نوشتن هر دور روی `MockLedger`)، و مقاومت بیزانسی. چون **Go و شبکهٔ Fabric در این محیط
نصب نیستند**، مسیر واقعی Fabric نوشته شده ولی آفلاین اجرا نشده (دقیقاً مثل Flower در فاز ۲ و
Opacus در فاز ۳). جزئیات: ADR-0006.

## ۱۰) فاز ۶ — مدل‌های حمله برای ارزیابی حریم خصوصی

تا اینجا **ادعا** کرده‌ایم که DP به‌ازای هر وجه از حریم خصوصی محافظت می‌کند. حالا می‌خواهیم این
را **عملاً ثابت** کنیم: یک «حمله‌کننده» بسازیم و ببینیم چه‌قدر می‌تواند هویت افراد را از روی
خروجی مدل بازیابی کند — و نشان دهیم با کم‌شدن ε (نویز بیشتر) حمله‌کننده ناتوان‌تر می‌شود. این
بخشی از **H5** است.

### ۱۰.۱ حملهٔ بازشناسی هویت (Re-identification)
سه حملهٔ نام‌بردهٔ پایان‌نامه — **شناسایی گوینده** (از صدا)، **تشخیص چهره** (از تصویر)، و
**استخراج موجودیت نام‌دار/NER** (از متن) — در عمل **یک** کار مشترک‌اند: از روی **بردار خلاصهٔ
(embedding) نویزی‌شدهٔ** یک وجه، حدس بزن این مربوط به کدام فرد است.

ما این را یک‌بار پیاده کردیم (`eval/attackers.py`، کلاس `ReidentificationAttacker`):
- برای هر فرد چند «نمونهٔ» embedding داریم. چندتا را **ثبت‌نام (enroll)** می‌کنیم (میانگینشان
  می‌شود «الگوی» آن فرد).
- بقیه را **آزمون (probe)** می‌کنیم: هر probe را به نزدیک‌ترین الگو (با **شباهت کسینوسی**) نسبت
  می‌دهیم.
- **نرخ موفقیت = چند درصد probeها درست به صاحبشان وصل شدند** (دقت top-1). خط پایهٔ شانس =
  ۱ ÷ تعداد افراد.

سه حملهٔ صدا/تصویر/متن فقط در این فرق دارند که embedding از کدام انکودر آمده — پس یک موتور،
سه کاربرد.

### ۱۰.۲ چرا روی دادهٔ ساختگی هم معنی دارد؟
نکتهٔ ظریف: در دادهٔ ساختگی **برچسب افسردگی تصادفی است** (بی‌معنی)، اما **هویت هر فرد یک سیگنالِ
واقعی است** — چون ویژگی‌های هر session از یک فرد مشخص ساخته شده. برای ساختن «چند نمونه از یک
فرد»، به ویژگی‌ها کمی **لرزش (jitter)** اضافه می‌کنیم (مثل چند جملهٔ متفاوت از یک گوینده). برای
همین منحنی حمله **واقعاً** معنی‌دار است: با ε بزرگ (نویز کم) بازشناسی آسان است؛ با ε کوچک
به‌سمت شانس سقوط می‌کند.

### ۱۰.۳ نگاشت ε به نویز
یک ε هدف را با **همان حسابدار RDP فاز ۳** به یک σ تبدیل می‌کنیم، و به embedding نویز گاوسی
به‌اندازهٔ `σ × noise_scale × (مقیاس embedding)` اضافه می‌کنیم. چون نویز نسبت به بزرگیِ خودِ
embedding مقیاس می‌شود، سوییپِ ε به‌خوبی از «بازشناسی کامل» تا «حد شانس» را پوشش می‌دهد.

### ۱۰.۴ حملهٔ استنتاج عضویت (Membership Inference)
یک حملهٔ دیگر: «آیا این نمونه در دادهٔ آموزشِ مدل بوده؟» مدل معمولاً روی نمونه‌های آموزشی
**مطمئن‌تر** است (خطای کمتر). حمله‌کننده با یک آستانه روی این سیگنال، عضو/غیرعضو را جدا می‌کند و
**مزیت (advantage = 2×AUC−1)** را گزارش می‌دهد (۰ = هیچ نشتی، ۱ = کامل). با ε بزرگ‌تر (نویز
کمتر) نشت بیشتر است.

### ۱۰.۵ جدول خروجی (`scripts/run_attack_eval.py`)
تعریف «انجام‌شده» فاز ۶: **جدول نرخ موفقیت حمله به‌ازای هر وجه و هر بودجهٔ ε** (ورودی فصل ۴).
اسکریپت `attack_success.json` (جدول کامل)، `attack_curve.jsonl` و نمودار
`attack_success_vs_epsilon.png` را می‌سازد. نمونهٔ خروجی روی دادهٔ ساختگی (خط شانس ≈ ۰.۰۳):

| ε | بازشناسی صدا | بازشناسی تصویر | بازشناسی متن | مزیت استنتاج عضویت |
|----|----|----|----|----|
| ۰.۵ | ۰.۰۹ | ۰.۰۵ | ۰.۰۶ | ۰.۴۷ |
| ۱۶ | ۱.۰۰ | ۰.۸۳ | ۰.۳۷ | ۰.۷۲ |

یعنی با بودجهٔ کوچک، حمله‌کننده تقریباً کور است؛ با بودجهٔ بزرگ، هویت‌ها لو می‌روند — دقیقاً
همان بده‌بستان حریم خصوصی/دقت.

> نکته: روی دادهٔ ساختگی **اعداد مطلق** نتیجهٔ نهایی پایان‌نامه نیستند؛ فقط سیگنالِ هویت واقعی
> است. اعداد واقعی با DAIC-WOZ می‌آیند. مقایسهٔ بین‌وجهی هم چون به جداپذیریِ ذاتیِ هر وجه در
> این مدل بستگی دارد، روی دادهٔ ساختگی گمراه‌کننده است. جزئیات: ADR-0007.

### تعریف «انجام‌شده» برای فاز ۶
✅ انجام شد: سه حملهٔ بازشناسی (صدا/تصویر/متن) + حملهٔ استنتاج عضویت + جدول موفقیت به‌ازای هر
وجه و هر ε، همراه تست‌های واحد و یکپارچه. منحنیِ هر وجه به‌روشنی با بزرگ‌شدن ε بالا می‌رود.

## ۱۲) چطور خودت اجراش کنی

> پیش‌نیاز: پایتون ۳.۱۱ به بالا. (در این محیط، به‌خاطر نبود اینترنت، تست‌ها با پایتون سیستم و
> `PYTHONPATH=src` اجرا شده‌اند؛ روی سیستم خودت با `uv` تمیزتر است.)

```bash
# ۱) ساخت محیط و نصب وابستگی‌ها
uv venv
uv pip install -e ".[dev]"

# ۲) اجرای همهٔ تست‌ها (باید همه سبز شوند)
uv run pytest

# ۳) آموزش مدل پایه (فاز ۱) روی دادهٔ ساختگی
uv run python scripts/train_baseline.py

# ۴) آموزش فدرال (فاز ۲) با ۸ کلاینت ناهمگن
uv run python scripts/run_federated.py --rounds 5 --num-clients 8

# ۵) آزمایش حریم خصوصی (فاز ۳): گزارش بودجه + نمودار دقت/ε
uv run python scripts/run_dp_sweep.py

# ۶) فاز ۴: مقایسهٔ تجمیع آگاه‌به‌قابلیت با FedAvg ساده
uv run python scripts/run_capability_federated.py --rounds 5 --num-clients 8

# ۷) فاز ۵: آموزش فدرال با ثبت حسابرسی روی بلاک‌چین (دفترکل قلابی، آفلاین)
uv run python scripts/run_federated_with_ledger.py --rounds 5 --num-clients 8

# ۸) فاز ۶: جدول موفقیت حملهٔ بازشناسی/عضویت برحسب وجه و ε
uv run python scripts/run_attack_eval.py
```

خروجی هر اجرا در پوشهٔ `experiments/<phase>/<نام اجرا>/` ذخیره می‌شود: تنظیمات استفاده‌شده،
فایل `metrics.jsonl` (معیارها) و چک‌پوینت/نمودار.

**نکته دربارهٔ اعداد:** چون داده ساختگی و تصادفی است، دقت‌ها بی‌معنی‌اند — هدف فعلی فقط
«درست‌کارکردن خط لوله» است. اعداد واقعی با دادهٔ DAIC-WOZ به‌دست می‌آیند.

## ۱۳) واژه‌نامه

| اصطلاح | به زبان ساده |
|--------|--------------|
| Tensor (تنسور) | آرایه‌ای از اعداد (بردار/ماتریس/…) |
| Model (مدل) | تابع بزرگ با وزن‌های قابل‌تنظیم |
| Parameter/Weight (وزن) | اعداد داخل مدل که در آموزش تنظیم می‌شوند |
| Gradient (گرادیان) | جهت شیب خطا؛ خلافش قدم می‌زنیم تا خطا کم شود |
| Learning rate (نرخ یادگیری) | اندازهٔ هر قدم اصلاح وزن |
| Epoch | یک بار عبور کامل روی همهٔ داده |
| Batch (دسته) | گروه کوچکی از نمونه‌ها که با هم پردازش می‌شوند |
| Modality (وجه) | یک نوع داده: صدا/تصویر/متن |
| Encoder (انکودر) | بخشی که یک وجه را به بردار خلاصه می‌کند |
| Embedding (بردار نهفته) | بردار خلاصه‌کنندهٔ یک ورودی |
| Fusion (فیوژن) | ترکیب بردارهای وجه‌های مختلف |
| Logit | خروجی خام سرِ طبقه‌بندی، قبل از تبدیل به احتمال |
| Sigmoid | تابعی که logit را به احتمال ۰ تا ۱ می‌برد |
| Loss (خطا) | عددی که میزان اشتباه مدل را می‌گوید |
| F1 / ROC-AUC | معیارهای کیفیت طبقه‌بندی |
| Federated Learning | آموزش بدون جمع‌کردن داده در یک‌جا |
| Client (کلاینت) | یک شرکت‌کننده (مثلاً بیمارستان) با دادهٔ محلی |
| Round (دور) | یک چرخهٔ کامل فدرال (پخش → آموزش محلی → میانگین) |
| FedAvg | میانگین وزن‌دار وزن‌های کلاینت‌ها |
| Differential Privacy (DP) | تضمین ریاضی که خروجی به یک فرد خاص وابسته نباشد |
| ε (اپسیلون) | بودجهٔ حریم خصوصی؛ کوچک‌تر = خصوصی‌تر، نویز بیشتر |
| δ (دلتا) | احتمال کوچک شکست تضمین DP |
| σ (سیگما) | ضریب نویز؛ بزرگ‌تر = نویز بیشتر = ε کوچک‌تر |
| Clipping (بریدن گرادیان) | محدودکردن سهم هر نمونه به سقف C |
| DP-SGD | آموزش با بریدن گرادیان + افزودن نویز |
| Privacy Accountant | ابزاری که ε خرج‌شده را حساب می‌کند (ما: RDP) |
| Re-identification risk | ریسک شناسایی هویت فرد از روی یک وجه |
| Capability vector (بردار قابلیت) | `[audio, video, text]` با ۰/۱؛ می‌گوید کلاینت چه وجه‌هایی دارد |
| Subgraph aggregation (تجمیع زیرگراف) | میانگین‌گیری هر انکودر فقط بین کلاینت‌های دارای آن وجه |
| Reputation (اعتبار) | امتیاز کلاینت از ترکیب حجم داده و سازگاری به‌روزرسانی |
| Consistency (سازگاری) | هم‌جهت‌بودن به‌روزرسانی با اجماع زیرگراف (شباهت کسینوسی) |
| EMA (میانگین متحرک نمایی) | هموارسازی امتیاز اعتبار بین دورها |
| Knowledge Distillation (تقطیر دانش) | انتقال دانش از مدل «معلم» به مدل «دانش‌آموز» |
| Teacher / Student (معلم/دانش‌آموز) | مدل سراسری منجمد / مدل محلی کلاینت |
| Byzantine robustness (مقاومت بیزانسی) | تاب‌آوری در برابر کلاینت‌های خراب یا مخرب |
| Blockchain (بلاک‌چین) | دفترکل تغییرناپذیر برای حسابرسی |
| Hyperledger Fabric | بلاک‌چین خصوصی/سازمانی که این پروژه استفاده می‌کند |
| Chaincode / Smart contract (قرارداد هوشمند) | برنامهٔ روی بلاک‌چین که قواعد نوشتن را اجرا می‌کند (زبان Go) |
| Ledger (دفترکل) | جایی که رکوردها ثبت می‌شوند؛ `MockLedger` نسخهٔ آفلاین آن |
| Append-only (فقط‌افزودنی) | فقط می‌شود اضافه کرد؛ بازنویسی ممکن نیست (مثل ε مصرف‌شده) |
| Re-identification attack (حملهٔ بازشناسی هویت) | حدس‌زدن هویت فرد از روی embedding نویزی‌شده |
| Speaker/Face/NER attacker | همان حملهٔ بازشناسی روی صدا/تصویر/متن |
| Membership inference (استنتاج عضویت) | حدس اینکه یک نمونه در دادهٔ آموزش بوده یا نه |
| Enroll / Probe (ثبت‌نام/آزمون) | نمونه‌های الگوسازی هر فرد / نمونه‌هایی که حمله می‌شوند |
| Seed (بذر) | عدد شروع تولید تصادفی؛ برای تکرارپذیری |
| Padding (پُرکردن) | افزودن صفر برای هم‌اندازه‌کردن دنباله‌ها |
| pydantic | کتابخانهٔ اعتبارسنجی تنظیمات |
